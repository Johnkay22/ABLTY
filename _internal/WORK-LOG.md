## 2026-10-05: Step 6, lock Premium so only the server can grant it
- **Who:** Cursor (cloud agent)
- **Branch / PR:** `cursor/step-6-lock-premium-bbab`, draft PR #136 (database only, no app change, no version bump)
- **What changed:** One new migration, `supabase/migrations/20261005000001_profiles_lock_entitlements.sql`. The existing tier lock only ran when a profile row was changed; it now also runs when a row is created, so a signed-in app user (or the public key) can no longer create their own profile row as Premium or tester, whether by a plain insert or an upsert. The same check will automatically cover `beta_premium_until` as soon as step 8 adds that column, with no further migration. The app's permission to delete or empty profile rows is removed (the app never deletes profiles; account deletion goes through the Worker with the service key, which keeps that permission), so a row can no longer be removed and recreated with different values. The function also pins its `search_path`, which clears the Supabase advisor warning noted in `LAUNCH-PLAN.md`. Signup (`handle_new_user`), the app's fallback profile creation (upsert with `tier: 'free'`), Claude's grants through the service role and the Worker's Stripe updates all keep working. Existing migrations were not edited. Rollback steps are in the migration's header comment. Also: PR #135 (steps 1 to 5) merged on 2026-10-05 at `20fccdf`; Status board updated.
- **Tests:** passed: `tests/postgres-profiles-entitlement-lock.sh` on a disposable PostgreSQL 16 cluster, run twice. It builds the live `profiles` shape, applies the real repo migrations in production order, first proves the hole exists (a signed-in user could insert a Premium row before the fix), then applies the new migration twice (idempotent) and checks 63 cases: signup trigger still creates a free profile and settings; fallback upsert accepted and repeatable; username and legal-acceptance writes accepted; update, upsert and insert of `tier` or `is_tester` denied for the signed-in user and the public key; delete and truncate denied; service role can set Premium, set tester, revert, insert a Premium row and delete; a Premium user cannot downgrade through the client (unchanged) but can still rename; after adding a `beta_premium_until` column, the client cannot set or clear it while the service role can; final grants, policy, triggers and function settings as expected. A GitHub workflow (`profiles-entitlement-lock-postgres.yml`) runs the same script on every migration change. Not run: anything against production, anything on a phone (nothing in the app changed).
- **Test correction (same day, after Johnny's review of PR #136):** the first version of the test left out two migrations that are live in production: `20260914000001` (the current signup function plus the case-insensitive username index) and `20260519000004` (the 30-day username rename cooldown trigger). Both are now applied in production order before the new migration. With the cooldown present, the old test's "premium user can still rename" step was unrealistic (it renamed the same account twice within seconds) and failed; that was a flaw in the test, not in the migration. The rename checks now follow the real rule: a first rename on a never-renamed account is accepted and the trigger stamps the time; a second rename moments later is rejected by the cooldown (as it should be, both for a free and a Premium account); the harness then moves that account's last-rename time back 31 days (test-only time travel, done by the test's database superuser, not by any app or client path) and the rename is accepted again. Other renames use accounts that have never renamed. New checks also prove the current signup function is the one running (a requested name that only differs in capitalisation from an existing one aborts the signup and leaves no account behind; a Google-style signup with no requested name gets a generated `seeker_` name). All privilege-denial and service-role checks are unchanged and still pass. Result: 63 checks, passed locally twice; the GitHub check on PR #136 reran with the corrected test (result recorded in the PR). The migration itself did not change.
- **Production:** nothing changed. Read-only checks only (live `profiles` columns, policies, grants and triggers, to make the test match the real database).

  - Step 5 second review (same day): (a) an empty queue is no longer read as "synced". The queue write can fail (full storage) and the in-memory fallback is lost on reload, so the newest five entries per table of the owner's own history on the phone (`ablty_sessions`, `ablty_zener`, `ablty_timestamp_all`, the durable record) are checked against the database by id and owner; ids the database holds are remembered (`ablty_sync_confirmed`, memory plus storage, last 60) so this costs one query per table once; missing ones are put back in the queue and uploaded (recovery); if the question itself fails the row says "Could not confirm that your latest results reached the cloud. Tap to check again." and never "synced". Reproduced in headless Chrome against the pre-fix code (after reload: "Synced to cloud", cloud empty) and confirmed fixed (after reload: the run is uploaded, then "Synced to cloud"). (c) A duplicate-key answer is now checked against the saved fields, not just id and owner: the existing row is read back and every submitted column compared (numeric strings, timestamp spellings and JSON key order are not differences); same owner with different contents stays queued as `content_mismatch`, never overwritten. (d) Permanently unresolved items are no longer offered "Tap to retry": the row says "N results could not be saved to the cloud: its save ID is already taken by another result. Retrying cannot fix this; it stays on this phone." and is not tappable unless something retryable is also waiting.
